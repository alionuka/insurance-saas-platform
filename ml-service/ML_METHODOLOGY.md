# ML Methodology — Insurance SaaS Platform

This document describes the machine-learning component of the platform: the
problem framing, datasets, model selection, evaluation, and integration with
the rest of the system. It is intended as the basis for the corresponding
section of the thesis text and as a reference for future contributors.

---

## 1. Problem statement

Two prediction tasks underpin the platform's underwriting and claims
workflows:

1. **Risk prediction.** Given a customer profile, estimate the probability
   that the customer will generate claims that exceed expected loss for
   the chosen product. The output is used to compute a personalised
   premium multiplier on top of a product's `basePremium`.

2. **Fraud detection.** Given a claim submission (numeric metadata plus a
   free-text incident description), estimate the probability that the
   claim is fraudulent. The output is surfaced to agents as a score and a
   `NORMAL`/`SUSPICIOUS` flag, supporting their review decisions.

Both tasks are framed as binary classification with a heavy class imbalance
typical of insurance: most customers are low-risk, most claims are
legitimate. The minority class is the operationally interesting one in
both cases (high-risk customers, fraudulent claims), so we evaluate using
metrics that account for imbalance — precision, recall, F1, and ROC-AUC —
rather than raw accuracy.

The baseline against which we compare is the original rule-based heuristic
(`if creditScore >= 750 → LOW risk`, `if amount > 50,000 → suspicious`).
Replacing those heuristics with trained models is the core ML contribution.

---

## 2. Datasets

Real labelled insurance data with permissive licensing is scarce. We
generate synthetic datasets whose feature distributions and target labels
follow plausible statistical patterns drawn from the actuarial literature.
This is acceptable for a thesis demonstrating methodology: the same
training/evaluation pipelines apply unchanged to a real labelled dataset
when one becomes available.

### 2.1 Risk dataset

Generated by `training/generate_risk_dataset.py`. **10 000 records.** Each
record represents one customer profile with the following features:

| Feature | Type | Distribution | Rationale |
| --- | --- | --- | --- |
| `age` | int, 18–80 | Normal(40, 12) clipped | Insurance buyers cluster around middle age. |
| `annual_income` | float | Log-normal(μ=10.8, σ=0.5) | Income data in real populations is heavy-tailed. |
| `credit_score` | int, 300–850 | Normal(680, 80) clipped | FICO-style distribution. |
| `years_customer` | int, 0–50 | Normal(8, 5) clipped | Tenure, used as a stability proxy. |
| `prior_claims` | int, ≥0 | Poisson(0.6) | Claim counts in real data are well-modelled by Poisson. |
| `region` | int, {0,1,2} | P=[0.5, 0.35, 0.15] | Urban / suburban / rural split. |

**Label.** A binary `high_risk` flag is sampled from a probability derived
from a logistic combination of the features. The combination includes
non-linear interactions (e.g. young drivers with prior claims have an
amplified risk) so that tree-based models have a chance to outperform a
purely additive linear model.

The resulting class balance is **18.9 % high-risk** — closer to a
realistic underwriting outcome than a balanced 50/50 split.

### 2.2 Fraud dataset

Generated by `training/generate_fraud_dataset.py`. **5 000 records.** Each
record represents one claim submission:

| Feature | Type | Notes |
| --- | --- | --- |
| `amount` | float | Log-normal; fraud claims biased toward higher amounts. |
| `claim_type` | categorical | AUTO / HEALTH / PROPERTY / LIFE. |
| `days_since_policy_start` | int | Fraud disproportionately occurs early. |
| `has_witnesses` | int {0,1} | No witnesses raises suspicion. |
| `prior_claims_count` | int | Poisson-distributed. |
| `description` | string | Free-text incident description. |

**Description templates.** Two pools of templates are sampled from with
placeholder substitution (street names, dates, hospitals, etc.):

- **Legitimate templates** are specific and detailed:
  *"Rear-end collision at the intersection of Main St and Maple Ave; minor whiplash and bumper damage; police report filed."*
- **Suspicious templates** are vague and use lexical markers associated
  with fraudulent claims in real-world studies (e.g. *"stolen", "no witnesses", "no documentation"*):
  *"Vehicle disappeared from parking lot, no security camera footage."*

Fraud rows draw from suspicious templates with 80 % probability;
legitimate rows draw from legitimate templates with 95 % probability. This
gives the text channel a learnable signal without making the task
trivially solvable.

**Class balance:** **9.2 % fraud** — consistent with industry estimates
of insurance fraud rates (5–10 %).

## 3. Risk prediction

### 3.1 Feature processing

All features are numeric except `region` (categorical). The preprocessing
pipeline applies:

- `StandardScaler` to the numeric columns,
- `OneHotEncoder` to `region` with `handle_unknown="ignore"`.

Both transformers are wrapped in a `ColumnTransformer` and prepended to
each candidate classifier so that scaling/encoding fit on training data
only, preventing test-set leakage.

### 3.2 Models compared

Three classifiers were trained on the same 80/20 stratified train/test
split, with a fixed random seed (42) for reproducibility:

1. **Logistic Regression** (`LogisticRegression`, `class_weight="balanced"`,
   `max_iter=1000`). Linear baseline; interpretable coefficients map
   directly to log-odds contributions per feature.
2. **Random Forest** (`RandomForestClassifier`, 200 trees, `max_depth=10`,
   `class_weight="balanced"`). Captures non-linear interactions;
   robust to feature scaling.
3. **Gradient Boosting** (`HistGradientBoostingClassifier`, 300 iterations,
   `max_depth=6`, `learning_rate=0.05`, `class_weight="balanced"`). Modern
   histogram-based boosting; competitive state of the art for tabular
   problems and handles class imbalance natively.

`class_weight="balanced"` instructs the trainer to weight the minority
class proportionally to its inverse frequency, which is the standard
remedy for imbalanced classification when the cost of false negatives is
high (here: missing a high-risk customer hurts more than mis-flagging a
low-risk one).

### 3.3 Evaluation

Metrics computed on the held-out test set (n = 2 000):

| Model | Precision | Recall | F1 | ROC-AUC |
| --- | --- | --- | --- | --- |
| Logistic Regression | 0.36 | 0.69 | 0.47 | **0.774** |
| Random Forest | 0.43 | 0.52 | 0.47 | 0.760 |
| Gradient Boosting | 0.40 | 0.60 | 0.48 | 0.759 |

Plots produced under `training/plots/`:

- `risk_roc_curves.png` — ROC curves for all three models overlaid.
- `risk_confusion_matrix.png` — confusion matrix for the best model.
- `risk_feature_importance.png` — feature importance for the Random Forest model.

### 3.4 Discussion

All three models cluster within 0.015 of each other on ROC-AUC; the
synthetic data signal is largely additive, with non-linear interactions
present but modest. Logistic Regression edges out the tree models on AUC
and is selected for production deployment because:

- **Interpretability.** Each feature's contribution to the log-odds is a
  single coefficient that domain experts and regulators can audit. This
  matters in insurance, where pricing must often be defensible to a
  regulator.
- **Inference speed.** A logistic regression call on a single row is a
  dot product; latency is sub-millisecond. Tree ensembles are slower per
  prediction.
- **Probability calibration.** Logistic regression is well-calibrated by
  construction. The output probability can be used directly as a risk
  score, without isotonic or Platt scaling.

The recall on high-risk (0.69) is above precision (0.36) by design. We
chose the operating point that prioritises catching risky customers over
avoiding false positives, since the cost of underwriting a truly risky
customer at a low premium is much higher than mildly over-quoting a
low-risk one. The threshold can be tuned at inference if business
priorities change.

## 4. Fraud detection

### 4.1 Feature processing

Three feature types are combined:

- **Numeric features** (`amount`, `days_since_policy_start`, `has_witnesses`,
  `prior_claims_count`) → `StandardScaler`.
- **Categorical** (`claim_type`) → `OneHotEncoder`.
- **Text** (`description`) → `TfidfVectorizer` with `max_features=500`,
  `ngram_range=(1, 2)`, English stop-words removed, `min_df=2`.

The TF-IDF vectorizer learns the vocabulary from training descriptions
only and produces a sparse 500-dimensional vector per claim. Bigrams are
included so multi-word indicators like *"no witnesses"* or *"unknown
cause"* are captured as single features.

All three transformers are wrapped in a `ColumnTransformer` that is
prepended to the classifier in a single `Pipeline`, ensuring that fit is
applied on training data only.

### 4.2 Two configurations compared

To isolate the contribution of the text channel, each candidate
classifier is trained twice:

- **Numeric only** — only the numeric and categorical features.
- **Numeric + TF-IDF** — full feature stack.

This ablation makes the value of the NLP component quantitatively
demonstrable.

### 4.3 Models compared

`LogisticRegression`, `RandomForestClassifier`, and
`HistGradientBoostingClassifier` — same configurations as in Section 3,
all using `class_weight="balanced"`.

`HistGradientBoostingClassifier` does not natively accept the sparse
matrix produced by `TfidfVectorizer`; we therefore omit it from the
*Numeric + TF-IDF* configuration. The other two classifiers cover the
text-augmented comparison adequately.

### 4.4 Evaluation

Metrics on the held-out test set (n = 1 000):

| Configuration | Model | Precision | Recall | F1 | ROC-AUC |
| --- | --- | --- | --- | --- | --- |
| Numeric only | Logistic Regression | 0.11 | 0.50 | 0.18 | 0.594 |
| Numeric only | Random Forest | 0.13 | 0.02 | 0.04 | 0.556 |
| Numeric only | Gradient Boosting | 0.13 | 0.26 | 0.17 | 0.539 |
| **Numeric + TF-IDF** | **Logistic Regression** | **0.57** | **0.83** | **0.68** | **0.905** |
| Numeric + TF-IDF | Random Forest | 0.59 | 0.71 | 0.64 | 0.876 |

Plots:
- `fraud_roc_curves.png` — ROC curves for all five trained pipelines.
- `fraud_confusion_matrix.png` — confusion matrix of the best pipeline.

### 4.5 Discussion

The numeric-only configuration is barely better than random
(AUC ≈ 0.55–0.59), confirming that the metadata alone does not separate
fraudulent from legitimate claims well in this dataset. Adding the text
channel raises AUC to 0.876 (Random Forest) and **0.905 (Logistic
Regression)** — a relative improvement of approximately 50 % in AUC and
a four-fold improvement in F1.

This is the expected behaviour: textual descriptions of a claim carry
considerable lexical signal (specificity of nouns, presence or absence
of supporting documentation, vague vs concrete temporal and spatial
references), and TF-IDF with bigrams is effective at extracting that
signal at modest computational cost.

The chosen production model is **Logistic Regression with TF-IDF + numeric
features**, with the same justifications as for risk: best AUC,
interpretable, and fast at inference. The recall of 0.83 means the model
catches roughly 83 % of fraudulent claims; the precision of 0.57 means
about 57 % of flagged claims are genuinely fraudulent. The remaining
mis-flags become routine review work for agents — an acceptable trade-off
in fraud detection, where a missed fraud costs orders of magnitude more
than a manual review.

## 5. Product recommendations

### 5.1 Approach

The recommendation endpoint implements **content-based filtering** using
TF-IDF vectorization of the product catalog and **cosine similarity**
ranking against a query vector derived from a customer's demographic
profile and reported life events. This is the canonical content-based
recommender pattern (Aggarwal 2016, *Recommender Systems: The Textbook*,
ch. 4). It was chosen over collaborative filtering because:

  - Collaborative filtering requires a sufficiently dense
    user-item interaction matrix, which a newly launched platform does
    not have. Content-based filtering works from the first session.
  - The cold-start problem (new customer or new product) is solved
    natively — recommendations require only the product description and
    the customer profile.
  - The catalog is small (8 products) so cosine similarity runs in
    constant time per query.
  - The output is interpretable: matched terms can be surfaced as part
    of the explanation, which is required by the platform's UI.

### 5.2 Catalog

The product catalog (`data/products_catalog.csv`) contains **8 synthetic
insurance products** spanning the four product types declared in the
Prisma schema:

| Type | Products |
| --- | --- |
| AUTO | SafeDrive Basic, SafeDrive Premium Plus |
| HEALTH | Essential Health Plan, Family Comprehensive Health |
| LIFE | SecureFuture Term Life, LegacyShield Whole Life |
| PROPERTY | RentSafe Renters Insurance, HomeShield Homeowners |

Each entry carries a `product_id`, `name`, `type`, and an extended free-text
`description` written to include domain-specific keywords (e.g.
*homeowners*, *retirement*, *family*, *premium*) so that TF-IDF matching
discriminates effectively across types.

### 5.3 Feature engineering

Per product, the feature text concatenates `name + type + description`. A
single `TfidfVectorizer` is fit over the eight concatenated documents
with the following parameters:

  - `max_features=200`
  - `ngram_range=(1, 2)`
  - `stop_words="english"`
  - `min_df=1` (small catalog — keep all terms)

This produces an 8 × 200 sparse term-document matrix.

At inference, the customer profile is translated to a free-text query
string by `build_query_keywords(age, income, life_events)`. The mapping
is deterministic and documented in
`training/train_recommendations_model.py`:

  - **Age brackets** contribute mild background terms (e.g. `young
    affordable basic` for under-30, `comprehensive` for 30–50,
    `retirement security` for 50+).
  - **Income brackets** add `affordable budget` for under-$35k or
    `premium luxury` for over-$100k.
  - **Life events** are the strong signal: each event contributes a
    fixed set of three keywords, repeated three times so that TF-IDF
    term frequency dominates the weaker age/income background. For
    example, `new_home` adds `home property homeowner house residence`
    each tripled.

The query string is then transformed by the same `TfidfVectorizer` and
cosine similarity is computed against every row of the product matrix.
The top-K (default K = 3) products by similarity are returned, together
with an explanation citing the highest-similarity match and the set of
recommended product types.

### 5.4 Evaluation

The model is evaluated on a panel of five canonical demographic profiles
designed to span the catalog's four product types. Each profile has a
manually annotated *expected top-1 type* derived from domain reasoning
(e.g. a 22-year-old with a $28k income should be top-recommended an AUTO
product; a 58-year-old planning retirement should see LIFE).

| Profile | Age | Income | Life events | Expected | Top-1 |
| --- | --- | --- | --- | --- | --- |
| young_low_income | 22 | 28 000 | – | AUTO | SafeDrive Basic ✓ |
| young_with_car | 26 | 45 000 | new_car | AUTO | SafeDrive Basic ✓ |
| family_with_children | 35 | 75 000 | marriage, child | HEALTH | Family Comprehensive Health ✓ |
| high_income_homeowner | 48 | 150 000 | new_home | PROPERTY | HomeShield Homeowners ✓ |
| near_retirement | 58 | 95 000 | retirement_planning | LIFE | LegacyShield Whole Life ✓ |

**Profile-match accuracy: 5/5 = 100%.** Reported similarity scores
range 0.31–0.49, well above the noise floor of 0.05–0.10 produced by
unrelated profile-product pairings.

This metric is an offline sanity check rather than a fully scientific
evaluation: the panel is small and was authored alongside the keyword
mapping. A more rigorous evaluation would require a labelled hold-out of
real customer–product preferences, which is on the roadmap once the
platform accumulates production interaction data.

### 5.5 Discussion

Content-based filtering is well-suited to this stage of the platform's
lifecycle. Two specific properties matter:

  - **Determinism and explainability.** The top-K ranking is reproducible
    and the matched terms can be surfaced in the response. For an
    insurance product, a customer rejecting a recommendation can be
    given a concrete reason ("we suggested *HomeShield Homeowners*
    because you reported a new home"), which is harder to provide with
    matrix-factorization recommenders that operate on latent factors.
  - **No cold-start gap.** Both new customers and new products are
    handled — the customer's first session produces real recommendations
    and a newly added product becomes available for ranking immediately
    after the catalog is re-vectorized at next service start.

The main limitation is that the recommender does not yet learn from
behaviour. A customer who dismisses health products and applies only for
auto policies still receives the same demographic-driven ranking. A
hybrid model that blends content similarity with implicit feedback
counts (applications, clicks) is the natural next iteration once
production data exists. This is recorded in §8 Future work.

## 6. Architecture and integration

The ML service is a stand-alone FastAPI process listening on
`http://localhost:8000`. The NestJS backend communicates with it via
HTTP using a thin `MlClientService` wrapper. Three endpoints are
exposed:

- `POST /risk/predict` — called from `ProductsService.quote()` (for
  personalised quotes) and `ApplicationsService.create()` (to attach a
  `RiskAssessment` row to every new application).
- `POST /fraud/detect` — called from `ClaimsService.create()` (to attach
  a `FraudAssessment` row to every new claim).
- `POST /recommendations` — currently unused by the dashboards; available
  for future personalisation features.

Models are loaded into memory once at process startup (`lifespan`
context manager). Inference is a synchronous call to `model.predict_proba`
on a single-row pandas DataFrame, returning in well under 10 ms in
practice. If a model file is missing the endpoint falls back to the
original rule-based heuristic, with a clear `Rule-based fallback:`
prefix in the response explanation, so the rest of the platform remains
operational during development and recovery.

The model artifacts (`risk_model.joblib`, `fraud_model.joblib`) are
produced by the training scripts under `training/` and stored in
`models/`. The training scripts also write JSON metric summaries
(`*_metrics.json`) for thesis tables and PNG plots
(`training/plots/*.png`) for inclusion in the document.

A dedicated service decoupled from the backend was preferred over a
co-located ML library import for three reasons:

1. **Language fit.** Python's scientific ecosystem (scikit-learn,
   pandas, NumPy) is unmatched for ML. NestJS in TypeScript is the
   right choice for the business backend but inappropriate for ML.
2. **Independent scaling and deployment.** ML inference can be a CPU
   hot-spot; running it as a separate process means it can be replicated,
   moved to a GPU host, or replaced with an async batch worker without
   touching the business backend.
3. **Clear separation of concerns.** The ML service has a narrow,
   versioned API surface (three endpoints, JSON in / JSON out). It can
   be tested and developed independently.

## 7. Limitations

- **Synthetic data.** The datasets are programmatically generated. The
  models therefore demonstrate methodology rather than predict on real
  populations. Migration to a real dataset would change feature
  distributions, label rates, and likely the relative ordering of
  models, but the training/evaluation pipeline is dataset-agnostic.
- **Single-region, single-language.** All descriptions are in English;
  the TF-IDF vocabulary is English. Multi-lingual support would require
  language detection or per-language pipelines.
- **No drift monitoring.** A production deployment would track input
  distribution shifts (e.g. average credit score of incoming applicants)
  and model performance over time, retraining periodically.
- **Static thresholds.** The 0.5 probability threshold for the
  `SUSPICIOUS` flag is a default; a deployed system would calibrate
  this against agent capacity and acceptable false-positive rates.
- **No SHAP / LIME explanations.** The current explanations are
  template-based heuristics. SHAP values per prediction would give
  per-feature contributions and are a natural next iteration —
  important for both regulatory defensibility and agent UX.

## 8. Future work

In rough priority order:

1. Replace the synthetic fraud descriptions with a real corpus (e.g.
   anonymised claim-narrative dataset from a partner insurer or a
   public source like the Texas Department of Insurance fraud reports).
2. Add SHAP-based per-prediction explanations and surface them in the
   admin and agent dashboards.
3. Extend the recommender from pure content-based to a hybrid model that
   blends cosine similarity with implicit-feedback signals (applications,
   policy purchases, claim history) once enough production interaction
   data accumulates.
4. Add periodic retraining triggered by drift detection on incoming
   production traffic.
5. Replace the joblib model files with a model registry (e.g. MLflow)
   for versioning, comparison, and rollback.
6. Add unit tests around the feature engineering and integration tests
   that exercise the full HTTP roundtrip from the backend through the ML
   service.

## 9. Reproducibility

To reproduce the trained models from scratch:

```bash
cd ml-service
python training/generate_risk_dataset.py     # writes data/risk_dataset.csv
python training/train_risk_model.py          # writes models/risk_model.joblib + metrics + plots
python training/generate_fraud_dataset.py    # writes data/fraud_dataset.csv
python training/train_fraud_model.py         # writes models/fraud_model.joblib + metrics + plots
python training/train_recommendations_model.py  # writes models/recommendations_model.joblib + metrics
```

All scripts use a fixed random seed (`42`). Re-running them on any
machine with the same Python and scikit-learn version yields byte-identical
output.

Pinning the dependency versions for full reproducibility:

```
scikit-learn>=1.3.0
pandas>=2.0.0
numpy>=1.24.0
joblib>=1.3.0
matplotlib>=3.7.0
```
